* Overview

~org-graph-block~ extends [[https://alhassy.github.io/org-special-block-extras][org-special-block-extras]] with a ~#+begin_graph~ block that
compiles native Org syntax — nested plain lists and two-column tables — into
[[https://graphviz.org][Graphviz dot]].

No raw dot required.  Nesting encodes edges; inline tables encode attributes.

** Setup

#+begin_src emacs-lisp
(require 'org-special-block-extras)
(require 'org-graph-block)
#+end_src

Graphviz must be on your ~PATH~ (~dot -V~ should work in a terminal).

** Pressing =C-c C-c=

Anywhere inside a ~#+begin_graph … #+end_graph~ block, ~C-c C-c~ renders a PNG
immediately.  The output filename is auto-generated unless you supply ~:file~:

#+begin_example
#+begin_graph directed :file my-diagram.png
…
#+end_graph
#+end_example

* Syntax Reference

| Construct                            | Dot equivalent                                                             |
|--------------------------------------+----------------------------------------------------------------------------|
| ~#+graph:~ table                     | ~graph [ … ]~                                                              |
| ~#+node:~ table                      | ~node [ … ]~                                                               |
| ~#+edge:~ table                      | ~edge [ … ]~                                                               |
| ~#+rank: n1 n2~                      | ~{ rank=same; n1; n2 }~                                                    |
| ~#+name: T~ + table                  | style template ~T~, used via ~:eval~                                       |
| ~+ NAME~ list item                   | node ~NAME~ declaration                                                    |
| indent ~+ CHILD~ under ~+ PARENT~    | edge PARENT → CHILD                                                        |
| ~∣ key ∣ value ∣~                    | node attribute; values are quoted for you                                  |
| ~∣ :id ∣ alias ∣~                    | cross-reference name for this node                                         |
| ~∣ :edge.KEY ∣ value ∣~              | attribute of the arc from the parent; a repeated KEY starts a parallel arc |
| ~∣ :to ∣ target ∣~                   | explicit outgoing edge; ~record.field~ targets a field                     |
| ~∣ :to.KEY ∣ value ∣~                | attribute of the ~:to~ edge just above                                     |
| ~∣ :eval ∣ T ∣~, ~∣ :to.:eval ∣ T ∣~ | splice template ~T~; explicit rows win                                     |
| ~∣ :children-rank ∣ same ∣~          | ~{ rank=same; <immediate children> }~                                      |
| ~∣ shape ∣ cluster ∣~                | ~subgraph cluster_ID { … }~ around the children                            |
| ~∣ shape ∣ record ∣~                 | children become fields; ~{}~ children flip the layout                      |

* Keys, Edges, Records, and Ports

** Two kinds of keys

By way of example, this item has one row of each kind:
#+begin_src org
+ Alonzo
  | label | Alonzo Church |
  | :id   | church        |
#+end_src
#+begin_src dot
church [ label="Alonzo Church" ];
#+end_src

A /plain/ key, such as ~label~, is a Graphviz attribute of the node, passed straight through. We
quote its value for you, so ~Alonzo Church~, ~#00ff00~, and ~x -> y~ all need no quotes; already-quoted
values, and ~<…>~ HTML labels, are left alone.

A key starting with a colon is /reserved/: it means something to the ~graph~ block itself, never to
Graphviz. A leading colon is never a Graphviz attribute, so the two kinds cannot clash. The reserved
keys are listed in ~org-graph-reserved-keys~:

| Key              | Meaning                                                   |
|------------------+-----------------------------------------------------------|
| ~:id~            | the node's name for cross-references; else its text       |
| ~:edge.KEY~      | attribute ~KEY~ of the arc from the parent                |
| ~:to~            | an extra arc, to the node, record field, or cluster named |
| ~:to.KEY~        | attribute ~KEY~ of the ~:to~ arc just above               |
| ~:eval~          | splice the rows of a ~#+name:~ template                   |
| ~:children-rank~ | ~{ rank=… }~ over this item's immediate children          |

An unknown ~:key~ is an error rather than a silently ignored attribute; so is a row in the
pre-colon spelling, such as ~| EDGE | label=x |~ or ~| to | B |~.

** Edges: nesting, ~:edge.KEY~, and ~:to~

Nesting makes an arc from parent to child; ~:edge.KEY~ rows on the child style that arc. Every
attribute is its own row, exactly like a node's, so there is one key-value syntax throughout.
Repeating a ~KEY~ starts another, parallel, arc:
#+begin_src org
+ client
  + server
    | :edge.label | request |
    | :edge.color | blue    |
    | :edge.label | retry   |
    | :edge.style | dashed  |
#+end_src
#+begin_src dot
client -> server [ label=request color=blue ];
client -> server [ label=retry style=dashed ];
#+end_src

Arcs that nesting cannot express use ~:to~. Each ~:to.KEY~ row styles the ~:to~ row just above it,
so rows read top to bottom like a small paragraph per arc:
#+begin_src org
+ Lisp
  | :to       | λ-calculus |
  | :to.label | borrows    |
  | :to.style | dotted     |
  | :to       | Fortran    |
#+end_src
#+begin_src dot
Lisp -> "λ-calculus" [ label=borrows style=dotted ];
Lisp -> Fortran;
#+end_src

A ~:to.KEY~ row with no ~:to~ row above it is an error. Mind that an item's table must come
/before/ its sub-items: a table after them belongs to no item, and is dropped.

** Templates: ~#+name:~ and ~:eval~

A ~#+name:~ table is a reusable bundle of rows; ~| :eval | NAME |~ splices it into a node, and
~| :edge.:eval | NAME |~ or ~| :to.:eval | NAME |~ into an arc. Explicit rows win over the template's,
wherever the ~:eval~ row sits:
#+begin_src org
,#+name: married
| color | "#cc3399" |
| dir   | both      |

+ Khadija
  | :to       | Muhammad |
  | :to.:eval | married  |
  | :to.color | red      |
#+end_src
#+begin_src dot
Khadija -> Muhammad [ dir=both color=red ];
#+end_src

Templates may themselves use ~:eval~, and so may the ~#+graph:~, ~#+node:~, and ~#+edge:~ tables; a
template that, directly or not, includes itself contributes nothing the second time.

** Records and ports: ~record.field~

With ~| shape | record |~, an item's immediate children become the /fields/ of one record node,
rather than nodes of their own; a child named ~{}~ groups its children, flipping the layout. An arc
reaches a field by ~record.field~ ---the same "this part of that thing" dot as ~:edge.label~:
#+begin_src org
+ struct1
  | shape | record |
  + left
  + middle
    | :id | mid |
    | :to | struct2.one |
  + right
+ struct2
  | shape | record |
  + one
  + {}
    + two
    + three
+ reader
  | :to | struct1.mid |
#+end_src
#+begin_src dot
struct1 [ shape=record label="left|<mid> middle|right" ];
struct1:mid -> struct2:one;
struct2 [ shape=record label="<one> one|{two|three}" ];
reader -> struct1:mid;
#+end_src

- A field's port is its ~:id~, else its text with spaces as underscores; ~struct1.The Middle~ works.
- A field is declared as a ~<port>~ exactly when it has an ~:id~ or some arc ends there ---~two~ and
  ~three~ above need none.
- Ports belong to their record, so two records may both have a ~head~ field: ~r1.head~ and ~r2.head~.
- ~a.b~ names a field only when ~a~ names a record; otherwise it is an ordinary node, such as
  ~v1.2~. Record and field names may contain dots themselves: ~org.el.v1.2~ is field ~v1.2~ of
  record ~org.el~.
- Graphviz spells ports ~record:field~; that is the spelling in the generated dot.

** Clusters

With ~| shape | cluster |~, an item becomes a box drawn around its children. An arc to or from a
cluster lands on the cluster's first node, clipped at its border:
#+begin_src org
+ Emacs
  + Packages
    | shape | cluster |
    + Org
    + Magit
#+end_src
#+begin_src dot
graph [ compound=true ]
subgraph cluster_Packages { label=Packages Org; Magit; }
Emacs -> Org [ lhead=cluster_Packages ];
#+end_src

1. Pressing ~C-u C-c C-c~ inside a ~#+begin_graph~ block shows the generated Graphviz dot source in
   a ~*org-graph dot*~ buffer instead of rendering a PNG.  A ~#+RESULTS:~ block containing a fenced
   ~#+begin_src dot … #+end_src~ is inserted (or replaced) in the org file so the source is preserved.

   For blocks where you always want dot output, add ~:C-c_C-c dot~ to the header:
   #+begin_example
   #+begin_graph directed :C-c_C-c dot
   …
   #+end_graph
   #+end_example
   Plain ~C-c C-c~ on such a block shows dot; ~C-u C-c C-c~ toggles back to PNG.
   The two controls compose via XOR — prefix always flips whatever the block default is.

2. Pressing ~C-u RET~ on any table row inside a ~#+begin_graph~ block inserts a new ~| key | value |~
   row interactively — a completion menu for the key, then one for the value (or a free-text prompt
   when the attribute accepts arbitrary strings).

   The menu is context-aware: it shows only attributes valid for the structural location of the table:
   - Table under ~#+graph:~ → graph-level attributes (~rankdir~, ~splines~, ~bgcolor~, …)
   - Table under ~#+node:~ → default node attributes (~shape~, ~style~, ~color~, …)
   - Table under ~#+edge:~ → default edge attributes (~arrowhead~, ~dir~, ~penwidth~, …)
   - Table under ~#+cluster:~ → cluster attributes (~bgcolor~, ~labelloc~, …)
   - Table on a list item → node attributes (same as above)

   The full attribute catalogue lives in the ~org-graph-attributes~ defcustom (customise via
   ~M-x customize-variable RET org-graph-attributes~); each entry has the form:
   #+begin_src emacs-lisp
   (:name "shape"
    :description "Shape of the node."
    :values ("box" "ellipse" "circle" …)  ;; nil → free-text prompt
    :valid-on (nodes))
   #+end_src

   Plain ~RET~ is unaffected — only the prefixed ~C-u RET~ triggers the completion.

  Now for your question: { rank=same; lisp; haskell } in Graphviz dot is a rank
  constraint. It tells the layout engine to place lisp and haskell on the same
  horizontal rank (row) — i.e., at the same vertical level in a top-down layout,
  or the same horizontal level in a left-right layout.
  
  Without it, the layout engine is free to stagger nodes vertically wherever
  their edge weights pull them. With rank=same, the listed nodes are pinned to a
  common baseline, which visually groups them as "peers at the same depth."

  ❯ How about we allow a node to have a new `| rank | same|` which means only the immediate children of that node are to be having the same rank?                                                                                                     

⏺ Nice idea. The semantics: if a node carries | rank | same |, we emit { rank=same; child1; child2; … } covering all its immediate children.
  
  A few design questions before we implement:

  1. Value flexibility — support only same, or also min/max/source/sink (the full Graphviz rank vocabulary)?
  2. Key name — rank clashes with the existing #+rank: preamble concept; fine since one is a node attribute and one is a directive, but worth confirming you're happy with rank as the row key.
  3. Scope — only immediate children, not grandchildren, right? (A cluster node with | rank | same | would be odd since its children become subgraph members; should we silently ignore rank on cluster nodes, or is that an edge case we don't care
   about?)

  My recommendation: support the full rank vocabulary (same, min, max, source, sink) since it's trivial and future-proofs the feature; ignore rank rows on record/cluster nodes silently. Agree?

❯ I was wrong, we still need to support the `#+rank` syntax, since some items are at the same level, but have no common parent!
