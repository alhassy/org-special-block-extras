1. HTML & LaTeX Setup   ignore

2. 🧙‍♂️ Write Once, Export Everywhere: Say Hello to org-special-block-extras

Tired of repeating yourself when writing in Org-mode for LaTeX and HTML exports? org-special-block-extras is your magical toolkit for creating custom Org-mode blocks and links that work seamlessly across backends —without diving into the dark arts of raw HTML or LaTeX!

2.1. 🎁 What Does It Do?

  • 🎨 Style with ease — add colors, badges, tooltips (from a dictionary, Emacs Help, or custom file), keystroke notations, inline editorial comments, or even colourful ASCII cows with fortune cookies.
  • 📚 Glossary support — embed hoverable documentation with doc: links and auto-generated glossaries.
  • 📦 Add interactive content: from collapsible detail sections and parallel columns to spoiler tags and equational proofs.
  • 🎛 Switch any block: :when (eq backend 'html), :noexport t, :let (N 7), :boxed "Title", :folded t, and :verbatim t, and :C-c_C-c ACTION work on every block —ours, yours, or Org's own src and quote blocks; see switches.
  • Use badge-style links to embed GitHub stars, Reddit subs, or custom project metadata via shields.io.
  • 🛠 Use org-defblock, org-deflink and org-deftag —Org, extended as one extends Lisp: each is declared like a cl-defun, with &optional and &key arguments; or, for the terse-minded, with a flattened arglist.
    • Create powerful custom blocks with org-defblock: Define a block once and export to LaTeX and HTML effortlessly. With header-args support like :color red :signoff "Thanks!" for locally customised exports. Each block is also a link and a tag, for free; and :fontify says how it looks in the buffer.
    • Use org-deflink to create custom links, as functions of their label and description.
    • Use org-deftag to create custom tags, as functions of the Org sections they tag.

3.1. Boxed Text —Calling out super duper info

﴾What You Write﴿ 
It can be useful to draw attention to some important text by
enclosing it in a [[doc:org-block/box][box]].

#+begin_box Uses of callout boxes
Such boxes often callout tips, warnings, cautionary info or
emphasises core information.
#+end_box
﴾What You Get﴿

It can be useful to draw attention to some important text by enclosing it in a box.

Uses of callout boxes

Such boxes often callout tips, warnings, cautionary info or emphasises core information.


﴾How It’s Implemented﴿ 
(org-defblock box (title "" background-color nil shadow nil frame-color nil title-background-color nil)
              "Enclose text in a box, possibly with a TITLE.

By default, the box's BACKGROUND-COLOR is green for HTML and red for LaTeX;
for LaTeX, there are also FRAME-COLOR and TITLE-BACKGROUND-COLOR.

SHADOW is an alternate style of boxing: It shows the contents in a centred
box with a shadow colour being the given non-nil value of SHADOW.
If SHADOW is a hexadecimal colour, it should be a string enclosed in double quotes.
More accurately, the following are all valid uses:

    #+begin_box title :shadow t
    #+begin_box title :shadow inset

    #+begin_box title :shadow \"pink\"
    #+begin_box title :shadow pink

    #+begin_box title :shadow (cyan pink orange yellow)
    #+begin_box title :shadow (cyan \"inset pink\" orange)
    #+begin_box title :shadow (:left cyan :right pink :deep-right orange :deep-left yellow)

Notice that prefixing colours with ‘inset’ causes the colour to be within the box,
rather than spread, with blur, around the box. The use of ‘inset’ swaps left and right.

The HTML export uses a padded div, whereas the LaTeX export
requires the tcolorbox package; Markdown, sans colours, gets a quote opening with TITLE in bold."
              (pcase (if (org-export-markdown-p) 'md backend)
                ('md (org-parse (format "#+begin_quote\n%s%s\n#+end_quote"
                                        (if (org-string-nw-p (format "%s" title)) (format "*%s*\n\n" title) "")
                                        raw-contents)))
                ;; Colours are named first, since tcolorbox options cannot take hex codes such as #CCFFCC.
                ('latex
                 (concat (org--latex-define-color "osbe-box-back" (or background-color "red!5!white"))
                         (org--latex-define-color "osbe-box-frame" (or frame-color "red!75!black"))
                         (org--latex-define-color "osbe-box-title" (or title-background-color "yellow!50!red"))
                         (format (concat "\\begin{tcolorbox}[title={%s},colback=osbe-box-back,colframe=osbe-box-frame,"
                                         "colbacktitle=osbe-box-title,coltitle=red!25!black, fonttitle=\\bfseries,"
                                         "subtitle style={boxrule=0.4pt, colback=yellow!50!red!25!white}]"
                                         "%s\\end{tcolorbox}")
                                 title contents)))
                (_ (format "<div style=\"%s\"> <h3>%s</h3> %s </div>"
                           (s-join ";" (list "padding: 1em"
                                             (format "background-color: %s" (org-subtle-colors (format "%s" (or background-color "green"))))
                                             "border-radius: 15px"
                                             "font-size: 0.9em"
                                             (org--box-shadow shadow)))
                           title contents))))

3.2. Folded Details —Let the user see stuff only if they're interested

﴾What You Write﴿ 
Sometimes there is a remark or a code snippet that is useful to
have, but not relevant to the discussion at hand and so we want to
/fold away such [[doc:org-block/details][details]]/.

#+begin_details Example use cases
+ ‘Conversation-style’ articles, where the author asks the reader questions
  whose answers are “folded away” so the reader can think about the exercise
  before seeing the answer.

+ Hiding boring but important code snippets, such as a list of import
  declarations or a tedious implementation.
#+end_details

Full syntax ~#+begin_details "title" :background-color "cyan" :title-color "green"~.
﴾What You Get﴿

Sometimes there is a remark or a code snippet that is useful to have, but not relevant to the discussion at hand and so we want to fold away such details.

Example use cases
  • ‘Conversation-style’ articles, where the author asks the reader questions whose answers are “folded away” so the reader can think about the exercise before seeing the answer.
  • Hiding boring but important code snippets, such as a list of import declarations or a tedious implementation.

Full syntax #+begin_details "title" :background-color "cyan" :title-color "green".


﴾How It’s Implemented﴿ 
(org-defblock details (title "Details" background-color "#e5f5e5" title-color "green")
              "Enclose contents in a folded up box, for HTML.

For LaTeX, this is just a boring, but centered, box.

By default, the TITLE of such blocks is “Details”,
its TITLE-COLOR is green, and BACKGROUND-COLOR is “#e5f5e5”.

In HTML, we show folded, details, regions with a nice greenish colour."
              (pcase backend
                ('latex (concat (org--latex-define-color "osbe-bg" background-color)
                                (org--latex-define-color "osbe-fg" title-color)
                                (format (concat "\\begin{quote}\n"
                                                "\\begin{tcolorbox}[colback=osbe-bg,colframe=osbe-fg,title={%s},sharp corners,boxrule=0.4pt]\n"
                                                "%s\n"
                                                "\\end{tcolorbox}\n"
                                                "\\end{quote}")
                                        title contents)))
                (_ (format (concat "<details class=\"code-details\" style=\"padding: 1em; background-color: %s; "
                                   "border-radius: 15px; color: hsl(157 75%% 20%%); font-size: 0.9em; "
                                   "box-shadow: 0.05em 0.1em 5px 0.01em #00000057;\">\n"
                                   "<summary><strong><font face=\"Courier\" size=\"3\" color=\"%s\">%s</font></strong></summary>\n"
                                   "%s\n"
                                   "</details>")
                           background-color title-color title contents))))

Src blocks fold too: the header argument :folded t exports a src block, exactly as Org otherwise would, inside a details block titled by its language; :folded "TITLE" picks the title. 

#+begin_src emacs-lisp :folded "How is it done?"
(org-defblock details …)
#+end_src

A page with many folded blocks may offer a button to unfold them all at once: [[toggle-details:][Show me everything]] is that button; pressed again, it folds them all. Without a description, it reads “Unfold all details”.

3.3. Nice Keystroke Renditions: C-h t

Anyone who writes about Emacs will likely want to mention keystrokes in an aesthetically pleasing way, such as C-u 80 - to insert 80 dashes, or C-c C-e h o to export an Org-mode file to HTML, or the useful M-s h ..

  • kbd:𝒳 will show a tooltip defining 𝒳, as an Emacs Lisp function, if possible. For example, kbd:C-h_t is C-h t; and likewise <kbd:M-s h .> is M-s h. (we need to use <...> since punctuation is not picked up as part of link labels). In contrast, kbd:nope renders as nope without a tooltip (nor a red border).

    You can also supply explicit tooltip description: [[kbd:key sequence][description]] will show as key sequence; i.e., the key sequence in nice key font along with a tooltip explaining it.

  • In Emacs itself, each of these displays as 〔C-x C-s〕: the kbd: markup becomes the brackets and each _ a space. Only the markup is displayed differently, so the keys stay editable as ever. Moreover, clicking one runs its keys —after asking, as elisp: links do— so readers may try them on the spot.

3.4. Remark —Inline footnotes, viz HTML tooltips and LaTeX notes in the margin

Sometimes you want to remark on without drawing too much attention, and so a tooltip via suffices.

﴾What You Write﴿ 
It can be annoying to make readers jump to the bottom of the page to
read a footnote.  Instead, I prefer to write an /inline [[doc:org-block/tooltip][remark]]/
containing, say, references or additional explanation.

   /[[tooltip:Allah][The God of Abraham; known as Elohim in the Bible]] does not burden a
       soul beyond what it can bear./ --- Quran 2:286

Or, without specifying an explicit label:

   /Allah[[tooltip:][The God of Abraham; known as Elohim in the Bible]] does not
       burden a soul beyond what it can bear./ --- Quran 2:286
﴾What You Get﴿

It can be annoying to make readers jump to the bottom of the page to read a footnote. Instead, I prefer to write an inline remark containing, say, references or additional explanation.

Allah  does not burden a soul beyond what it can bear. — Quran 2:286

Or, without specifying an explicit label:

Allah°  does not burden a soul beyond what it can bear. — Quran 2:286


﴾How It’s Implemented﴿ 
(org-defblock tooltip (marker "°")
              "Show CONTENTS, as Org, in a tooltip on MARKER; hovered on a desktop, tapped on a phone.
In LaTeX, MARKER is followed by CONTENTS as a margin note, numbered as footnotes are, as the margin block's are;
in beamer, whose slides have no margins, as a footnote."
              (if (equal backend 'latex)
                  (concat marker (if (org-export-beamer-p)
                                     (format "\\footnote{%s}" contents)
                                   (org--latex-margin-note "{\\thefootnote}" "\\marginparwidth" "gray!80" contents
                                                           "\\refstepcounter{footnote}")))
                (concat (org--html-tooltip raw-contents marker) "&emsp13;")))

A tooltip opens when its word is hovered with a mouse, or tapped on a phone; it closes when we leave both, tap elsewhere, or press Escape. Its text is Org, exported as Org, so it may hold links —clickable, since moving into the tooltip keeps it open— and any other markup; an Elisp docstring is shown just as it is written. The machinery is tooltips.js, about eighty lines with no dependencies, in the look of tooltips.css; both are inlined into each exported page, which so fetches nothing for them.

Org's own footnotes are such remarks too: in HTML, each footnote's number is a tooltip of its definition, the footnotes section staying below, for print; in LaTeX, each is a margin note, as the margin block's are, numbered as footnotes are. All three of Org's spellings serve: an anonymous [fn::…], a named [fn:NAME] defined elsewhere, and a named inline [fn:NAME: …], which later [fn:NAME] references share.

﴾What You Write﴿ 
The Quran was revealed over 23 years[fn::From 610 to 632 CE, in Mecca then Medina.], and the
Torah[fn:torah] and the Gospel[fn:injil: /Injil/, given to Jesus.] are honoured in it as earlier
scriptures; the Gospel[fn:injil] is named in it a dozen times.

[fn:torah] /Tawrat/, given to Moses; see [[https://en.wikipedia.org/wiki/Tawrat][Tawrat]].
﴾What You Get﴿

The Quran was revealed over 23 years1, and the Torah2 and the Gospel3 are honoured in it as earlier scriptures; the Gospel3 is named in it a dozen times.

Footnotes:

3.5. Glossaries —Define a term once, cite it with doc:𝒳

A doc:𝒳 link shows the documentation of 𝒳 as a tooltip in HTML, and as a glossary reference in LaTeX. Here 𝒳 is an Emacs Lisp function or variable, a word in the English dictionary —via WordNet's wn, should we have it— or, best of all, a term of our own.

﴾What You Write﴿ 
The ~doc~ link type can be used to show tooltips for Emacs Lisp commands such as

                         doc:thread-last
                         
However, it can also be used for your own definitions/glossary.
First define a term as follows, which does not render anything in the resulting HTML.

                 #+begin_documentation Category Theory :label cat
                 A theory of typed composition; e.g., typed monoids.
                 #+end_documentation

Then you can refer to it using the given :label, if any:

                             doc:cat
  
Or else refer to it with underscores in lieu of spaces:

                       doc:Category_Theory

Either approach renders the name of the term, not the way its referenced.
If you want to change what's rendered, provide a description:

                  [[doc:cat][abstract nonsense]]

Finally, if ~doc~ gets a label that is not an Emacs Lisp command, variable, nor a user-defined
definition via #+begin_documentation, then we try to look up its definition via the dictionary:

                          doc:happiness
﴾What You Get﴿

﴾How It’s Implemented﴿ 
(org-deflink doc
  "Export O-LABEL as itself, or as the provided O-DESCRIPTION,
 along with a tooltip that shows the user's
 documentation-glossary for o-LABEL and using that entry's name
 when no O-DESCRIPTION is provided."
  :let (entry (org-docs-get o-label)
        name (cl-first entry)
        docs (cl-second entry)
        display-name (or o-description name))
  :help-echo (format "[%s] %s :: %s" o-label name docs)
  :face '(custom-button)
  :export (progn
            (add-to-list 'org--docs-actually-used (list o-label name docs))
            (pcase o-backend
              ('html (org--html-tooltip docs display-name (org--docs-plain-p o-label)))
              ;; Make the current word refer to its glossary entry, and declare the location
              ;; that the glossary should refer back to; see the GLOSSARY of `org-link/show'.
              ('latex (format "\\hyperref[o-glossary-%s]{%s}\\label{o-glossary-declaration-site-%s}"
                              o-label display-name o-label))
              (_ display-name))))

Our own terms are data in an Org file: an entry is either a documentation block, which exports nothing, or a heading tagged :documentation:, which exports as an ordinary section. The heading's title is the term's name, its :DOC_KEYS: property lists the labels by which we cite it, and its own text is the definition. Either way, the name with underscores in lieu of spaces is a label too; e.g., doc:Category_Theory. Moreover, show:GLOSSARY lists every term the page cites, wherever it sits.

﴾What You Write﴿ 
Our glossary, listing every term this page cites ---even those cited further below:

                                     show:GLOSSARY

* Category Theory                                                   :documentation:
:PROPERTIES:
:DOC_KEYS: cat
:END:
A theory of typed composition; e.g., typed monoids.

* Using our terms

A glossary entry may instead be a block, which exports nothing:

#+begin_documentation Monoid :label mon
A set with an associative binary operation that has a unit.
#+end_documentation

Then, doc:cat studies [[doc:mon][monoids]] and their kin.

Our glossary, listing every term this page cites —even those cited further below:

(org-defblock documentation
              (name (error "Documentation block: Name must be provided")
                    label nil show nil color "green"
                    ;; A heading tagged :documentation: is an entry in its own right; see `org--docs-read-buffer'.
                    :tag nil)
              "A glossary entry: CONTENTS defines NAME, cited as doc:LABEL; a heading tagged :documentation: is one too.

The entries live in ‘org--docs’.

A documentation entry may have its LABEL, its primary identifier,
be:
1. Omitted
2. Given as a single symbol
3. Given as a many aliases '(lbl₀ lbl₁ … lblₙ)

The third case is for when there is no canonical label to refer to
an entry, or it is convenient to use multiple labels for the same
entry.

In all of the above cases, two additional labels are included:
The entry name with spaces replaced by underscores, and again but
all lower case.

unless SHOW is non-nil, in which case they are shown
using the ‘box’ block, with the provided COLOR passed to it.

  * Category Theory                                  :documentation:
    :PROPERTIES:

              ;; Should the special block show something upon export?
              (if show (org--blockcall box name :background-color color raw-contents) ""))

Terms we cite across many files go in a library: a list of Org files in org-docs-libraries, whose entries —blocks and headings alike— every doc:𝒳 link may cite. The files are read, not exported, so loading them is quick; M-x org-docs-load-libraries reloads them after an edit, and M-x org-docs-insert inserts a doc:𝒳 link by searching all the terms we have.

A radio target is a term too: in A <<<monoid>>> is a set with an associative operation and a unit., the target names the term and its paragraph defines it; so doc:monoid cites it, in the same file or, from a library, in any other.

Finally, a package's whole API makes a glossary of its own: the package-docs block exports a table of the public functions, macros, and variables that a feature defines, each name a doc:𝒳 link whose tooltip is its documentation.

3.6. Parallel ---Place ideas side-by-side, possibly with a separator

﴾What You Write﴿ 
Reduce the amount of whitespace noise in your articles by using the
[[doc:org-block/parallel][parallel]] block to place ideas
side-by-side ---with up to 𝓃-many columns.

----------------------------------------------------------------------

#+begin_parallel 2
*“Soft Columns”:* Writing ~#+begin_parallel 𝓃 :bar BAR~ will produce
𝒏-many parallel columns, possibly separated by solid rules, or a
“bar”. /This style allows text to freely move between columns,
depending on the size of the browser, which may dynamically shrink
and grow./ The value ~BAR~ can either be ~t~, ~nil~, or any
(backend)-valid colour specification; such as ~red~ or ~green~.
#+end_parallel

----------------------------------------------------------------------

#+begin_parallel 25% 50% 25% :bar green

*“Hard Columns”:* Alternatively, /for non-uniform column widths, 𝓃 may
instead be a specification of the widths of the columns./

#+columnbreak:  
However, this extra flexibility comes at an additional cost: The
contents of the block must now contain /𝓃-1/ lines consisting of
~#+columnbreak:~, when the specification determines 𝓃-many columns.

#+columnbreak:
Goodbye (“God-be-with-ye”) to the right!

#+end_parallel

# In the Soft Columns style above, any ‘#+columnbreak:’ are merely ignored.

In summary, articles can get lengthy when vertical whitespace is
wasted on thin lines; instead, one could save space by using
/[[doc:org-block/parallel][parallel]] columns of text/.
﴾What You Get﴿

Reduce the amount of whitespace noise in your articles by using the parallel block to place ideas side-by-side —with up to 𝓃-many columns.

“Soft Columns”: Writing #+begin_parallel 𝓃 :bar BAR will produce 𝒏-many parallel columns, possibly separated by solid rules, or a “bar”. This style allows text to freely move between columns, depending on the size of the browser, which may dynamically shrink and grow. The value BAR can either be t, nil, or any (backend)-valid colour specification; such as red or green.

3.12. Quotations, cited ---#+begin_quote KEY

3.15. Markdown export —What survives GitHub, and how to change it

Exporting to Markdown, with ox-md or ox-gfm, our blocks see backend as html, since md derives from it; (org-export-markdown-p) tells the two apart. A Markdown renderer, such as GitHub's, keeps only some HTML: it strips every style, class, <style>, and <font>, yet keeps <details>, <kbd>, <mark>, <ins>, <abbr title>, <img>, and $$ maths.

Work as-is
badge, melpa, kbd, details, solution, rename, and show export just as they do to HTML, and so render on GitHub —sans colours.
Markdown of their own

these blocks export to Markdown idioms, rather than HTML.

4. Make your own blocks and links —A developer's guide

Every block and link above is made with the very tools below, so a new one of our own is a defun away.

4.1. Make your own blocks with org-defblock

We declare a block just as we declare a function with cl-defun: the block's main argument —written right after #+begin_NAME— is its &optional argument, and its header arguments are its &key arguments. In the body, backend names the current export backend and contents the block's Org-parsed contents. 

(org-defblock note (&optional (title "Note") &key (color "teal"))
  "Call out CONTENTS under TITLE, tinted COLOR."
  (pcase backend
    ('html (format "<div style=\"border-left: 4px solid %s; padding-left: 1em\"><b>%s</b>%s</div>"
                   color title contents))
    (_     (format "\\textbf{\\color{%s}%s} %s" color title contents))))

Now the following binds title to "Heads up" and color to red; omit either, and its default is used. The main argument may also be given by its name, as a keyword: #+begin_note :title "Heads up" is the same block. 

#+begin_note "Heads up" :color red
Mind the gap.
#+end_note

For any backend derived from HTML or LaTeX —org-reveal's, ox-hugo's, ox-gfm's, beamer's, or our own— backend is html or latex, so one rendering serves them all. To single one out, we ask Org's own org-export-current-backend; by way of example, a docsy alert in Hugo: 

(org-defblock noteblock (&optional (title "Note") &key (color "primary"))
  "A note: a docsy alert in Hugo, a noteblock environment in LaTeX, a box elsewhere in HTML."
  (cond ((org-export-derived-backend-p org-export-current-backend 'hugo)
         (format "{{%% alert title=\"%s\" color=\"%s\" %%}}\n%s\n{{%% /alert %%}}" title color raw-contents))
        ((equal backend 'latex) (format "\\begin{noteblock}\n%s\n\\end{noteblock}" contents))
        (t (format "<div class=\"note\">%s</div>" contents))))

In similar spirit, (org-export-markdown-p) and (org-export-beamer-p) single out Markdown and beamer.

Every block is also a link, with the label as main argument and the description as contents: [[note:Heads up][Mind the gap.]].

Even Org's own blocks ---quote, verse, center, example, src, export, and comment— are fair game: an (org-defblock verse …) overrides every #+begin_verse, saying so in *Messages*. To leave some to Org, a handler hands them back; by way of example, a verse signed by its poet, else Org's own: 

(org-defblock verse (&optional poet)
  "A verse, signed by POET; sans one, Org's own verse."
  (if (org-string-nw-p poet)
      (format "\\begin{verse}\n%s\n\\end{verse}\n--- %s" contents poet)
    (org-parse (org-builtin-block "verse" raw-contents))))

Our own quote does just this: given a citation, it is ours; else, Org's own. Moreover, defaults may change long after the block is defined; e.g., (org-set-block-header-args note :color "orange").

One definition gives three uses: a block, a link, and a tag. A section tagged :note: exports as a note block around its own text, up to the next heading; the tag's underscore-separated items form the main argument —tags cannot hold spaces— and the section's properties supply keyword arguments by name. So all three of these agree: 

#+begin_note "Heads up" :color red
Mind the gap.
#+end_note

[[note:Heads up][Mind the gap.]]

* Why bother?        :note_Heads_up:
:PROPERTIES:
:COLOR: red
:END:
Mind the gap.

Likewise, the package's own blocks are links and tags too; e.g., :details_Hint: folds a section's text away under the title Hint. Try tagging a heading :red: —or :blue:, :teal:, … any of the 19 colours— and its text exports in that colour.

Should we not want all three, the options :link nil and :tag nil decline the link and the tag, whereas :block nil keeps only the link and tag —e.g., (org-defblock note (&optional (title "Note") :tag nil) …). The variable org-defblock-links-and-tags sets whether blocks come with links and tags by default; its documentation weighs the trade-off —chiefly namespacing: every block claims the link type NAME: and the tag :NAME:. So, should :red: already mean something else in our headings, we set org-defblock-links-and-tags to nil before loading this package. For just a link, or just a tag, there are org-deflink and org-deftag, below.

A tag wraps only its section's own text, since a block cannot hold a heading. By way of example, in * Abstract :abstract: with a ** Aside beneath it, the aside stays outside the box. Declaring :tag [:subsections MODE] picks what becomes of subsections:

  • ignore —the default, as with :tag t— leaves them outside the block;
  • error refuses a tagged section that has any, naming both headings; and
  • recurse wraps each subsection's own text in a block of its own, with the same arguments, unless the subsection carries the tag itself.

A block may also say how it looks in our Org buffers, via the option :fontify: below, #+begin_proof shows as Proof., #+end_proof as ⏹, and the contents in italics too. Each part is optional; the text itself is untouched, only displayed differently. 

(org-defblock proof (&optional title :fontify [:begin "Proof." :end "⏹" :face 'italic]) …)

Convenience: For the terse-minded, the arglist may be flattened into the main argument and its default, followed by key-value pairs. The block above is then 

(org-defblock note (title "Note" color "teal") …)

The full story is at C-h o org-defblock.

4.2. Make your own links with org-deflink

An Org link [[NAME:label][description]] is a function of its label and description; so, we declare one as we would a cl-defun, then say how it exports and how it looks within Emacs. 

(org-deflink shout (label &optional description backend)
  "Shout the description, else the label."
  :face '(:weight bold :foreground "red")
  :help-echo (format "I'll shout %s" (or description label))
  :export (format (if (eq backend 'latex) "\\textbf{%s}" "<b>%s</b>")
                  (upcase (or description label))))

Then shout:hello and [[shout:hello][hey there]] export as HELLO and HEY THERE. The arglist names the label, description, and export backend, in that order; any may be omitted from the end, and (description "…") gives a default. Besides :export, the keys :face, :help-echo, :follow, :keymap, :display and :let customise the link within Emacs; C-h o org-deflink has the details.

Convenience: The arglist may be omitted, whence the anaphoric names o-label, o-description and o-backend are used instead: 

(org-deflink shout
  "Shout the description, else the label."
  :export (upcase (or o-description o-label)))

4.3. Tags are functions of Org sections: org-deftag

image:

Just as a special block is a function on a region of text, so too a tag is construable as a function on an Org section (Reddit post). By way of example, the following renders any section tagged :quote: as a <blockquote>. 

(org-deftag quote (&optional (color "black") &key cite)
  "HTML export a section as a <blockquote>, its text coloured COLOR, crediting CITE."
  (insert "\n#+html:" (format "<blockquote style=\"color: %s\">" color))
  (org-next-visible-heading 1)
  (insert (if cite (format "\n#+html: <cite>%s</cite>" cite) "") "\n#+html: </blockquote>"))

As with cl-defun, the &optional arguments are positional: the underscore-separated items after the tag's name bind them in order. Any the tag omits are read from the section's property of the same name, and then default. The &key arguments are read from properties only —handy for lots of named info. 

* Tags are functions of Org sections        :quote_blue:
* Tags are functions of Org sections        :quote:
:PROPERTIES:
:COLOR: blue
:CITE: Musa
:END:

When both the tag and a property give an argument, the tag wins.

Convenience: The arglist may be flattened into name-default pairs, all positional; (org-deftag quote (color "black") …) is the above, sans cite.

The body runs at export time, with point where the heading used to be —it has been erased, along with its property drawer, so we reinsert o-heading if we want it. The body may mention

  • o-backend —the export backend, such as html or latex;
  • o-heading —the heading's text, sans the tag;
  • o-properties —all of the section's properties, as a plist such as (:color "blue"); and
  • o-drawer —the erased property drawer, as text, should we want it back.

Sections without the tag are left untouched, property drawers and all.

Often, all we want is for a section to export as one of our special blocks; for that, we need no tag of our own —see the :tag t option of org-defblock, above. By way of example, :details_Hint: folds a section's text away under the title Hint.

The full story is at C-h o org-deftag.

4.4. C-c C-c for your own blocks

Org's C-c C-c does the obvious thing at point: it runs a src block, ticks a checkbox, recalculates a table. Our special blocks may join in; one call gives every #+begin_NAME … #+end_NAME block a C-c C-c action.

For a single block, the :C-c_C-c switch suffices: #+begin_quiz :C-c_C-c my/check-answers makes C-c C-c within that block call my/check-answers; a Lisp form, rather than a function name, is evaluated instead. For every block of a kind, we register a handler: 

(org-defblock shout () "Upcase the contents." (upcase contents))

(org-defblock-add-cc-handler "shout"
  (lambda ()
    (message "C-c C-c inside a shout block!")
    t)) ;; Non-nil claims the keypress, so Org does nothing else with it.

The handler takes no arguments and runs with point inside the block. To see the block itself, we jump to its #+begin_shout line and call org-special-block-after-point, which yields the block's name, main argument, keyword arguments, contents and extent.

For a complete worked example, we may mimic the graph block's handler, org-graph–cc-handler. It

  • finds its block via (re-search-backward "^[ \t]*#\\+begin_graph\\b") then (org-special-block-after-point "graph");
  • reads the block's keyword arguments, so #+begin_graph :C-c_C-c dot changes what C-c C-c does;
  • honours C-u via current-prefix-arg —showing the dot source rather than rendering a PNG;
  • inserts a #+RESULTS: section after #+end_graph, just as src blocks do; and
  • returns t, claiming the keypress.

It is registered with a one-liner at the end of org-graph/org-graph-block.el: 

(org-defblock-add-cc-handler "graph" #'org-graph--cc-handler)

The dispatcher itself —a single function on org-ctrl-c-ctrl-c-hook— lives in org-ctrl-c-ctrl-c-for-special-block.el.

4.5. C-c ' to edit a block in its own buffer

Just as C-c ' edits a src block in a buffer of its language, so too it edits every special block —ours, or any #+begin_𝒳 at all— in an Org buffer; C-c ' again writes the contents back. Org keeps all it already does: a table, a link, or a src block within a special block is edited as ever.

A block may instead choose its buffer's mode: the option :edit-indirect-mode MODE makes C-c ' open the block's contents in a buffer in MODE. By way of example, the graph block is declared with :edit-indirect-mode org-graph-edit-mode, an Org mode that completes Graphviz attributes. 

(org-defblock poem (&optional title :edit-indirect-mode text-mode)
  "Set CONTENTS in italics, under TITLE."
  (format "<h3>%s</h3><em>%s</em>" title contents))

For an action beyond an edit buffer, (org-defblock-add-edit-special-handler "poem" #'my-handler) registers any function of no arguments, just as C-c C-c handlers are registered —see org-special-block-indirect-edit.el.

4.6. C-c C-v C-d to split a block in two

Just as C-c C-v C-d splits a src block at point, so too it splits any special block, after Kaushal Modi's trick; each piece keeps the block's whole #+begin_ line, header arguments and all. By way of example, with point at the start of Two., 

#+begin_tip Mind
One.
Two.
#+end_tip

becomes 

#+begin_tip Mind
One.
#+end_tip

#+begin_tip Mind
Two.
#+end_tip

At a line's end, the split falls after that line; an active region is split off as a piece of its own; and C-u C-c C-v C-d puts a heading between the pieces. In a src block within a special block, it is the src block that is split, as ever. The command is org-special-block-split, should you want it on a key of its own.

4.7. Hover for a block's arguments: eldoc

With point on a #+begin_NAME or #+end_NAME line, or on a NAME: link, the echo area —or eldoc-box, should we use it— shows how the block is called, defaults and all, along with the first line of its docstring: 

#+begin_details TITLE="Details" :background-color "#e5f5e5" :title-color "green": Enclose contents in a folded up box, for HTML.

This needs no setup beyond org-special-block-extras-mode, and works for our own blocks too. For the full story of a block, C-h o org-block/NAME.

Likewise, completing on a #+begin_ line ---M-TAB, or any completion popup— offers every block's name beside the first line of its docstring, and Org's own blocks beside them; a popup's documentation pane shows the block's whole docstring.
